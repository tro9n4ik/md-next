# Переезд на VPS

Механизм экспериментальный. Автоматические тесты не заменяют сквозное испытание на отдельном VPS. Самостоятельный запуск переноса агентом запрещён без согласия пользователя.

## Три действия в панели

1. **Подготовить VPS.** Проверяется закреплённый SSH-ключ и отличие серверов по machine-id. Выбирается последний подписанный commit main с успешными push-проверками CI и секретов. Обновляется ОС нового VPS; после необходимой перезагрузки мастер ожидает SSH и новый boot-id. Затем устанавливается чистая изолированная панель. Только после её готовности создаётся зашифрованный бэкап исходной установки и выполняется пробное восстановление.
2. **Финальная синхронизация.** После внешней проверки каждого VPN-протокола исходные службы останавливаются, создаётся финальный согласованный снимок и обновляются данные нового VPS. Выбранный билд целевого сервера остаётся закреплённым; самопроизвольное обновление main не меняет начатый перенос.
3. **Активировать.** Требуется отдельное подтверждение переключения и внешней проверки протоколов. Активируется только финальный снимок со свежей проверкой базы и конфигурации. DNS пользователь переключает вручную.

До активации доступна ссылка отмены. Она восстанавливает зашифрованный снимок чистой целевой установки и возобновляет исходные службы, если они были остановлены. После начала активации автоматический обратный перенос запрещён: сначала нужно согласовать данные двух серверов.

Вместо консоли показаны текущий этап, понятное сообщение, индикатор выполнения и код ошибки. Процент не выдумывается. SSH-отпечаток загружается при заполнении адреса и порта, затем пользователь независимо сверяет его с консолью провайдера. Причина недоступности кнопки указана рядом с формой.

## Бэкап и восстановление

Формат `.mdmove` использует Scrypt и аутентифицированное шифрование Fernet. Пароль комплекта нужен на всех этапах, включая отмену, и должен храниться отдельно. Обычный логический бэкап панели не заменяет этот комплект.

Режим `clean-install` переносит согласованный SQLite-снимок, ключи установки и VPN, сертификаты, сайт-заглушку и данные дополнительных компонентов. Системные unit-файлы и глобальная конфигурация Nginx исходного сервера не заменяют файлы нового билда. HTTPS настраивается в конфигурации чистой установки с исходными сертификатами. Если использовалась защита Nginx, она генерируется кодом нового билда; карта блокировок сохраняется как данные.

Перед записью новой базы Alembic применяет миграции к временной копии. Неизвестная схема или попытка перейти на меньшую версию останавливает восстановление до замены данных. Старые снимки режима `snapshot`, в том числе бэкап для отмены, требуют совпадения версии и commit. Это сохраняет точность отката.

Зашифрованные снимки текущей попытки сохраняются на исходном сервере в `/var/lib/md-next/migration/trial.mdmove` и `final.mdmove` с доступом root. Базовый снимок нового VPS — `before-restore.mdmove`. Незавершённый импорт отмечается `importing.json`: до успешной проверки он блокирует активацию. Проверка готовности не подменяется ручным созданием маркеров.

## Дополнительные компоненты

WARP регистрируется отдельно на новом VPS; его действующая регистрация с исходного сервера не копируется. Официальный репозиторий запрашивается с заголовком продукта. Ошибки HTTP и сети показываются без секретов.

Для AdGuard Home сохраняются YAML-конфигурация и файлы фильтров. Бинарный файл исходного сервера не включается в бэкап. Скачивается та же версия из официального релиза GitHub под архитектуру нового VPS с обязательной проверкой SHA-256 из метаданных релиза. Отсутствие контрольной суммы останавливает установку. Архив не распаковывается произвольными путями: читается только файл бинарной программы.

Служба AdGuard создаётся заново под отдельным системным пользователем. Интерфейс доступен только на `127.0.0.1:3001`, DNS — `127.0.0.1:5354`. Сохраняются пользовательские правила и настройки фильтров; журналы запросов и статистика не переносятся. Отдельные TLS/DHCP-настройки требуют ручной подготовки и блокируют автоматическую настройку. Чужая существующая установка не перезаписывается. Служба включается в автозапуск только при активации.

## Ограничения и проверки

Нужны root SSH, поддерживаемый Debian/Ubuntu, минимум 2 ГиБ RAM вместе со swap и 5 ГиБ свободного диска. Недостаток оперативной памяти исходного сервера блокирует создание комплекта, а не снижает защитный порог.

Пакетные блокировки ожидаются до 900 секунд. Таймеры apt приостанавливаются на время подготовки и возвращаются в исходное состояние. После обновления допускаются не более двух автоматических перезагрузок; каждая ожидается до пяти минут. Перед отправкой пароля повторно проверяется SSH-ключ, после перезапуска — machine-id и boot-id.

В `MDNEXT_MIGRATION_STAGING=1` выключены бот и фоновые задачи, API не меняет данные. Пробная проверка VPN выполняется явно и не означает согласия на активацию. Обязательны `nginx -t`, проверка Xray, применение конфигурации AmneziaWG, готовность WARP/AdGuard при их использовании и HTTPS панели. После этого пользователь проверяет реальные подключения с внешнего устройства на новом IP.

Секреты не попадают в статус API. Временный файл запроса root/0600 удаляется после чтения worker. Журнал установщика доступен только root. Операции защищены блокировками; повторный запуск не должен обходить незавершённый импорт или активацию.

Основные ошибки: `MIG_BUILD` — нет подходящей подписанной сборки; `MIG_SCHEMA` — несовместимость базы; `MIG_TARGET_OCCUPIED` — чужая установка; `MIG_REBOOT_TIMEOUT` — сервер не вернулся после перезагрузки; `MIG_NGINX_CONFIG`, `MIG_XRAY_CONFIG`, `MIG_AWG_CONFIG`, `MIG_WARP`, `MIG_ADGUARD` — проверка соответствующего компонента не прошла. При ошибке сначала проверьте этап и состояние обоих серверов; не запускайте финальное переключение повторно вслепую.
