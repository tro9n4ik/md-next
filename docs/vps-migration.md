# Переезд в два действия

Введите IP нового чистого Debian/Ubuntu VPS и root SSH-пароль и нажмите «Начать переезд». Используется SSH-порт 22. Ключ SSH закрепляется при первом подключении; его смена останавливает работу до отправки пароля. Автоматическое получение отпечатка не заменяет независимую проверку сервера.

Мастер обновляет ОС, обрабатывает нужную перезагрузку, устанавливает последний подписанный прошедший CI билд GitHub, создаёт зашифрованный бэкап и восстанавливает данные в изолированной панели. Рабочая панель продолжает обслуживать клиентов. После проверок появляется карточка «Подтвердить / Отменить». Подтверждение означает, что пользователь проверил подключения на новом IP; оно запускает свежую финальную синхронизацию, повторную проверку и активацию. После успешного подтверждения пользователь меняет IP в DNS-записях своих доменов. До активации отмена восстанавливает исходное состояние. После начала активации автоматический откат запрещён.

Email администратора и ручной пароль комплекта в этом сценарии не нужны. Staging-установщик пропускает ACME/email и использует временный сертификат до восстановления исходных сертификатов. Бэкап остаётся зашифрованным Scrypt/Fernet: для каждой попытки root создаёт случайный секрет. Параметры подключения и секрет хранятся только в `/var/lib/md-next/migration/managed-session.json` (root, 0600), доступны лишь привилегированному помощнику; API получает только признак управляемой сессии. Это защищённый правами ОС файл, не отдельное шифрование его содержимого. После завершения или отмены SSH-пароль удаляется, а ключ зашифрованного бэкапа сохраняется в root-only `recovery-key-<id>.json` для восстановления; `recovery-key.json` содержит последний ключ. Ключи предыдущих попыток не перезаписываются. Эти файлы не входят в переносимый комплект. Не копируйте ключ рядом с публично доступным бэкапом. Старая попытка с ручным паролем поддерживается прежним API; если пароль не был сохранён сервером, автоматическая отмена без него невозможна.

Системные файлы создаются средствами нового билда, база мигрируется на временной копии до замены данных. Ключи, клиентские данные, сертификаты, настройки WARP и конфигурация/фильтры AdGuard сохраняются. AdGuard скачивается той же версии из официального GitHub-релиза под архитектуру VPS с проверкой SHA-256. Чужие компоненты не перезаписываются. TLS/DHCP AdGuard и нестандартные наборы HTTPS-сертификатов требуют ручной подготовки. Журналы запросов AdGuard и его статистика не входят в комплект.

Службы загрузки устанавливаются автоматически. Nginx, Xray, backend и md-next-awg включаются в автозапуск после активации. AWG запускается только при наличии конфигурации и маркера `awg-boot-enabled`; в staging маркер отсутствует. Существующий интерфейс принимается без отключения клиентов. Сначала запускаются сеть/WARP/AdGuard и Xray, затем AWG и backend. Настройка порядка сама не перезапускает рабочие службы. ip_forward сохраняется через sysctl, policy routing восстанавливает awg-routing.py. Применение VPN при проверке выполняется от md-next; строгая проверка владельца черновиков сохраняется.

Подготовка проверяет отличие серверов, ОС, память/диск, apt-блокировки, точный commit и состояние импорта. Перезагрузка целевого VPS ожидается до пяти минут, с проверкой ключа, machine-id и нового boot-id; максимум два цикла. Незавершённый импорт блокирует перезапись. Для проверки нужны nginx -t, Xray, AmneziaWG, используемые дополнительные компоненты и HTTPS. Синтетические проверки не заменяют клиентские испытания. Прямые IP в старых профилях не меняются автоматически.

Последний реальный переезд проверен пользователем в Happ, MTProto и Amnezia; текущая версия сценария в два действия требует отдельного сквозного испытания. Не запускайте реальный перенос, перезагрузку рабочего сервера или смену DNS без согласия оператора.
