# Telegram MTProto

Добавил отдельный профиль клиента для встроенного прокси Telegram. Сохранил существующие VPN-профили и подписки.

## Включение

1. Обновите панель до сборки с этим компонентом. Переустанавливать ноды не нужно.
2. Выберите активную выходную ноду.
3. Откройте «Протоколы → Telegram». По умолчанию использую отдельный TCP-порт 8445. Разрешите его в файрволе сервера и у хостинга. Публичный адрес в параметрах Reality должен вести на панель.
4. Укажите доступный HTTPS-домен FakeTLS. Не обещаю, что конкретное доменное имя обеспечит работу в любой сети. При смене домена или порта нужно заново выдать клиентам ссылки.
5. Включите канал «Telegram MTProto» и примените настройки. Для существующих клиентов создам профили; при добавлении новых клиентов также создам отдельный секрет.
6. В карточке клиента откройте «Telegram MTProto» и выдайте ссылку или QR-код. Клиент открывает ссылку в Telegram и подтверждает прокси. Бот выдаёт личную страницу подписки, на которой также есть подключение Telegram.

Если все клиенты отключены, просрочены или исчерпали лимит, процесс MTProto остановлю. При появлении доступного клиента запущу его снова. По умолчанию канал выключен.

## Компонент и выход

Использую [dolonet/mtg-multi](https://github.com/dolonet/mtg-multi), закреплённую версию 1.13.0, MIT. Бинарники не включаю в репозиторий. Сохраняю лицензию установленного компонента в `/etc/md-next-mtproto/LICENSE`. При первом применении непустого набора доступов скачиваю архив из GitHub Releases и проверяю записанный в коде SHA256. Если загрузка недоступна, применение завершится ошибкой; неизвестный бинарник не запускаю. Подготовку системной службы выполняю при обновлении панели, скачивание — только по необходимости.

Запускаю отдельную systemd-службу `md-next-mtproto.service` от пользователя `md-next-mtproto`. Публичный вход — выбранный TCP-порт панели, без захвата 443. Секреты в БД зашифрованы через ключ установки. Runtime-конфигурация находится в `/etc/md-next-mtproto/config.toml`, доступна только root и группе службы. Не публикуйте её и клиентские ссылки.

Клиентский трафик отправляю через единственный SOCKS-прокси `127.0.0.1:10909`. В Xray закрепляю этот вход за активной нодой перед пользовательскими правилами и правилами WARP. При отсутствии активной ноды использую blackhole. Правила WARP для других протоколов и трафик Telegram-бота эта настройка не меняет. Фоновый DNS и маскировочные запросы компонента не являются пользовательскими VPN-профилями.

Для соединений MTProto с дата-центрами Telegram использую IPv4 (`prefer-ip = "only-ipv4"` в корне TOML). По умолчанию компонент предпочитает IPv6; если на ноде он недоступен, подтверждение SOCKS ещё не означает, что Telegram ответит, и клиент может оставаться в состоянии подключения. При первом применении исправления перезапускаю только службу MTProto, чтобы новый режим вступил в силу. Секреты, порт и ссылки клиентов сохраняются; последующие синхронизации неизменённого конфига не требуют перезапуска.

## Отзыв и учёт

При отключении профиля, паузе или удалении клиента удаляю его секрет из runtime-набора. При перевыпуске заменяю ключ. Использую SIGHUP: остальные неизменённые пользователи сохраняют сеансы. Дожидаюсь совпадения отпечатка применённых секретов из локального API; одного успешного systemctl reload недостаточно. Если подтверждение не получено, останавливаю службу и возвращаю ошибку применения.

Срок и месячный лимит проверяю при обычной периодической синхронизации условий подписок. Статистика доступна только на `127.0.0.1:10910/stats`; не открывайте этот порт наружу. Учитываю bytes_in/bytes_out отдельно для каждого профиля и включаю их в общий и месячный расход клиента. Курсор храню в БД в одной транзакции с начислением, чтобы перезапуск backend не начислял весь трафик повторно. Перезапуск MTProto распознаю по started_at.

Это периодический учёт, а не точный биллинг: трафик между последним опросом и остановкой/удалением секрета может не попасть в статистику, лимит может быть превышен до следующего опроса. MTProto не выполняет функции обычного VPN; совместимость звонков зависит от клиента Telegram.

## Проверка после обновления

Проверьте из внешней сети подключение двух разных клиентов, затем приостановите одного и убедитесь, что второй продолжает работать. Проверьте перевыпуск секрета, истечение срока и месячный лимит. При смене активной ноды повторите подключение; без доступной ноды пользовательский трафик должен блокироваться. Локальные автоматические проверки и запуск бинарника не заменяют эту проверку на реальном VPS и в приложении Telegram.
