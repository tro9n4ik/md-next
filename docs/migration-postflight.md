# Проверки переноса после установки — 2.5.14

## DNS нового VPS

Проверка выполняется после проверки принадлежности и чистоты VPS, до запроса билда GitHub и apt, повторяется после установки и перед проверками пробного/финального переноса и активацией. Системное разрешение имён запускается в ограниченном дочернем процессе; дополнительно проверяются настроенные DNS-серверы, включая ответ REFUSED и неполный ответ. Ожидание getaddrinfo ограничено восемью секундами, одна прямая DNS-проба — шестью.

Если используется systemd-resolved, DNS неисправен и нет нестандартных DNS-доменов, механизм предварительно проверяет DNS-over-TLS с TLS-проверкой имени у Google и Cloudflare. В конфиг попадают только доступные провайдеры. Если ни один не прошёл проверки, установка останавливается с MIG_TARGET_DNS, прежний конфиг сохраняется. После изменения конфиг проверяется повторно без локального кеша; при ошибке восстанавливается прежний файл. Сетевые адреса, маршруты, firewall и VPN-службы не меняются. Настройка хранится в /etc/systemd/resolved.conf.d/70-md-next-verified-dns.conf. Частный/split DNS и системы без активного systemd-resolved требуют ручной подготовки, автоматической замены для них нет.

Проверка DNS VPS не подтверждает DNS мобильного оператора и не доказывает устранение всех причин недоступности панели с телефона.

## Данные и сертификаты

SSH-worker передаёт закреплённый IP целевого VPS в restore --target-address. В копии базы перед импортом обновляется adguard.bootstrap_ip, если AdGuard включён. Пробный и свежий финальный снимки обрабатываются одинаково; при rollback привязка не меняется. Для ручного восстановления комплекта с AdGuard теперь требуется явно указать IP цели.

Формат комплекта по-прежнему содержит обычные файлы, а не произвольные ссылки. Восстановление проверяет renewal-конфиг Certbot и находит полное поколение archive с совпадением cert, chain, fullchain и privkey. Только после проверки всех файлов создаются относительные live-ссылки. Несовпадение останавливает импорт до замены данных. Повторное восстановление и отмена учитывают эти ссылки.

Новые комплекты сохраняют список исполнимых renewal-hooks; исполнимость восстанавливается только внутри каталогов pre/deploy/post Certbot. Для старого комплекта распознаётся штатный hook MD-Next; нестандартные старые hooks без сведений о правах требуют ручной проверки. Hooks во время переноса не запускаются. Таймер Certbot отключается до импорта и остаётся отключённым до активации, включая перезагрузку staging-сервера; отмена восстанавливает прежние флаги таймера. Выполняющееся продление блокирует замену файлов. Штатный standalone renewal переводится на webroot только при наличии известного HTTP challenge location; нестандартные плагины и hooks требуют ручной проверки.

Отдельный auth-logrotate не создаётся, если штатный nginx wildcard уже обслуживает этот лог. Чужой nginx-конфиг не переписывается; конфликт с пользовательской правкой останавливается для ручной проверки.

## Обновление со старой панели

Старый updater продолжает выполнять свой прежний код до завершения процесса. Поэтому подготовка host.key в новом updater сама по себе не исправляет первый переход с версии 2.5.11.

Если старый процесс запускает Alembic от md-next, а корень /var/lib/md-next недоступен для записи, идентификатор атомарно сохраняется в уже доступном каталоге данных data/host.key с режимом 0600. Затем root-этап установки создаёт канонический host.key с той же солью и передаёт доступ службе. Смена machine-id между этими этапами не меняет ключ. Конфликт двух идентификаторов приводит к отказу. Опубликованная миграция 0022 не изменена. Запись в корневой каталог для md-next не разрешается.

## Испытания

Локальные целевые тесты включают восстановление, повтор и откат, DNS REFUSED/таймауты/откат конфигурации, права ключа и совместимость старого updater. На отдельном RF VPS проверены фактические права непривилегированного процесса, шифрование/расшифровка синтетической записи до и после root-подготовки, относительные ссылки Certbot и штатный logrotate --debug в изолированном дереве. Google DoT на этом стенде отклонял соединение, Cloudflare DoT отвечал; в коде учитывается такой частичный отказ. На рабочем VPS настоящий перенос, активация, откат или перезагрузка этими испытаниями не выполнялись.
