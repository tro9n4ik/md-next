# Публикация сборки для обновления панели

Панель разрешает установку только текущей вершины `main`, для которой GitHub подтверждает подпись коммита и успешное завершение обязательных проверок. Успешный CI сам по себе не заменяет подпись.

## Порядок публикации

1. Подготовить изменения в отдельной ветке и открыть pull request в `main`.
2. Дождаться успешных обязательных проверок. Не обходить защиту ветки.
3. Выполнить слияние через GitHub с созданием merge-коммита либо squash-коммита. Не переносить неподписанную вершину ветки прямым обновлением ссылки `main`. Rebase and merge не гарантирует подтверждённую подпись итогового коммита.
4. Проверить именно новую вершину `main`: `GET /repos/tro9n4ik/md-next/commits/main` должен вернуть `commit.verification.verified: true`. При другом результате сборку не объявлять готовой.
5. Дождаться успешных push-запусков `.github/workflows/ci.yml` и `.github/workflows/secrets.yml` для того же полного SHA. Проверять свежие запуски, а не результаты предыдущего коммита или только PR.
6. В панели повторно нажать «Проверить обновления». Установку рабочей панели выполняет администратор отдельно.

## Если GitHub возвращает unsigned

Это означает отсутствие подписи коммита, а не ошибку пароля, DNS или сервера панели. Не отключать проверку подписи в API, интерфейсе, установщике или механизме переезда.

Уже опубликованный неподписанный коммит не переписывать и не подменять. Подготовить следующий коммит через обычный проверенный pull request, получить подтверждённую GitHub подпись новой вершины и дождаться CI. Исходные исправления должны остаться в её истории.

Пример: сборка `7d0b889` содержала исправления блокировок SQLite, отката нод и лимитов Nginx и прошла CI, но GitHub вернул `verified: false, reason: unsigned`. Блокировка её установки соответствует требованиям обновления.

См. [проверку подписей в документации GitHub](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification).
