# Экспериментальный транспорт узлов на Go

Самостоятельный исследовательский модуль. Не подключён к панели, рабочим нодам
или установщику MD-Next. Echo-демон принимает только loopback-адреса;
отдельный `mdnt-tunnel` предназначен для явно настроенного Linux-стенда.
Это **не QUIC и не HTTP/3**; невидимость для DPI не подтверждена и не обещается.

Измерения и незакрытые критерии: [результаты стенда](TEST_RESULTS.md).

## Границы первой версии

Реализованы аутентифицированные UDP-датаграммы, AES-128-GCM, случайный padding,
раздельные ключи направлений, фильтр CID, защита от повторов, расчёт сменяемого
порта, loopback echo-проба и отдельный Linux TUN-forwarder. Он проверяет длину
IPv4/IPv6 и передаёт в TUN только аутентифицированные пакеты разрешённого peer.

Первым потребителем должен стать **канал управления** панель–нода: ограниченные
сообщения состояния и команды с идентификаторами, сроком действия, подтверждением
и идемпотентностью. Нельзя автоматически считать доставку UDP выполнением команды.
Пользовательский IP-туннель остаётся экспериментом, со своими маршрутами,
MTU и ресурсными лимитами; контроль перегрузки пока не реализован. Сейчас нет ни RPC,
ни интеграции с прежним агентом. Собственного Go-агента в проверенном дереве
MD-Next не найдено; сторонний amneziawg-go не использован как его замена.

## Формат v1

| Поле | Размер | Назначение |
| --- | ---: | --- |
| Первый байт | 1 | `0x43`: фиксированный бит и длина PN=4 |
| CID | 8 | Усечённый HMAC-SHA256 от временного слота |
| Номер пакета | 4 | Big-endian, счётчик отправителя |
| Соль сессии | 16 | CSPRNG, новая при запуске и переполнении PN |
| Шифротекст | переменный | uint16 длины + данные + случайные 16–128 байт |
| Тег GCM | 16 | Аутентификация всего заголовка и тела |

Полезные данные ограничены 1380 байтами. Накладные расходы 63–175 байт,
но padding дополнительно ограничен так, чтобы UDP-пакет был не больше 1452 байт
(1480 с внешними IPv4/UDP). Соль — расширение нашего формата, которого нет
в QUIC short header. PN не скрыт, header protection и TLS-handshake отсутствуют.
Настоящий QUIC устанавливает ключи через TLS и защищает часть первого байта и PN;
случайный похожий заголовок не доказывает наличие HTTP/3-сессии.
См. [RFC 9000](https://www.rfc-editor.org/rfc/rfc9000.html) и
[RFC 9001](https://www.rfc-editor.org/rfc/rfc9001.html).

## Криптография и ограничения

Общий секрет — 32 случайных байта **на пару узлов**, передаваемых независимым
защищённым способом. Используются стандартные `crypto/aes`, `crypto/cipher`,
`crypto/hkdf`, `crypto/hmac`, `crypto/rand` Go 1.24+. HKDF разделяет CID, выбор
порта и AEAD, а также направления uplink/downlink. Ключ AES дополнительно
зависит от соли сессии и слота. Nonce GCM: четыре нулевых байта + uint64 PN.
При переполнении uint32 меняется соль до следующего шифрования.

CID — дешёвый предварительный фильтр по таблице трёх временных слотов, а не
аутентификация. Данные выдаются только после AEAD и проверки replay-window.
Окно допускает перестановку последних 64 пакетов, повтор и слишком старый пакет
отбрасываются. Состояние ограничено 1024 аутентифицированными сочетаниями соли
и слота; живое replay-состояние не вытесняется. Неверный AEAD не создаёт запись.
Скачок часов назад не открывает уже истёкшие слоты. Допускается соседний слот
в обе стороны; сильная рассинхронизация приводит к отказу, не к снятию защиты.

**Перезапуск получателя требует нового общего секрета на обоих концах.**
Replay-состояние пока хранится в памяти. CLI до приёма пакетов атомарно создаёт
и fsync-ит маркер использования ключа в приватном постоянном каталоге и отказывается
использовать его повторно. Не удаляйте маркер ради повторного запуска с тем же
ключом. При использовании библиотеки вызывающий обязан применять этот guard
или реализовать эквивалентную защиту. Автоматические rekey, согласование эпох,
PFS и постоянное replay-состояние ещё не реализованы. Владение общим секретом
позволяет выдавать себя за peer: это не сертификатная идентичность узла.

Слот и порт по умолчанию меняются каждые 25 секунд; диапазон ограничен 1024
портами. CID одной пары повторяется внутри слота. Это допускает корреляцию.
Ротация порта не гарантирует прохождение NAT/фаервола, обход ограничений или
неизменный RTT. Нет rate limiter, congestion control и публичного listener;
ограничение памяти не устраняет CPU DoS при известном CID. Не открывайте демон
в интернет. Echo отвечает только на аутентифицированные сообщения.

## Проверки

```sh
go vet ./...
go test -race ./...
go test -run '^$' -fuzz FuzzOpen -fuzztime 5s
go test -run '^$' -bench . -benchmem
go build -o mdnt ./cmd/mdnt
python3 tests/linux_namespace.py          # только план
sudo python3 tests/linux_namespace.py --run
```

Последний тест создаёт отдельный network namespace, поднимает только loopback,
проверяет nftables-правило через `nft -c`, перенаправляет порты 38010–38013
в один UDP-сокет 38000 **внутри namespace**, проверяет отказ для мусорного
пакета, 32 AEAD echo-пробы и смену портов. Затем создаёт непостоянный TUN,
выставляет MTU 1024 и проверяет удаление при закрытии дескриптора.
Namespace и его firewall удаляются в `finally`. IPv4 — предварительный целевой
режим; полноценные IPv6/PMTUD/маршрутизация пока не поддерживаются.
Семантика redirect: [документация nftables](https://wiki.nftables.org/wiki-nftables/index.php/Performing_Network_Address_Translation_(NAT)).

На старом VPS 88.210.35.93 проверены race-тесты, vet, fuzz, loopback через
nftables и жизненный цикл TUN в отдельном namespace. Сеть хоста и рабочий VPS
не менялись. Тестовый ключ и временные файлы удаляются после проверки.

Замер кодека на Go 1.26.0 linux/amd64, Common KVM CPU, GOMAXPROCS=1,
payload=1024: Seal ~1984 нс (516 MB/s, 6 alloc), Seal+Open ~2935 нс
(349 MB/s, 8 alloc). Это микробенчмарк кодека с padding, **не скорость туннеля**:
системные вызовы, сеть, потери и TUN в него не входят. Нулевая нагрузка CPU
и гигабит на заданной доле ядра не обещаются.

## Дальнейшие шаги

1. Ревью модели угроз и аутентифицированного согласования/смены ключей;
   безопасное восстановление после рестарта без ручной смены секрета.
2. Ограниченный канал управления: framing, ACK, дедлайны, backpressure,
   rate limiting, идемпотентность и границы полномочий.
3. Полноценный PMTUD, congestion control и испытания IPv6/перестановки на WAN.
4. Доведение измерений потерь/RTT/CPU до критериев технического задания.
   Любые выводы о DPI требуют независимых сетевых испытаний.

Прототип дорабатывается в `feature/node-transport-go-hardening`; включение в main или рабочую
сеть требует отдельного решения пользователя.

## TUN и ротация

`go build -o mdnt-tunnel ./cmd/mdnt-tunnel` собирает отдельный Linux-бинарник.
Явно задаются bind/peer IPv4, направление, root-only файл общего ключа и
постоянный закрытый каталог состояния. До приёма пакетов демон ждёт UP/MTU1380
до 30 секунд; адреса и маршруты настраивает стенд. Секрет нужно менять на обоих
peer после перезапуска: защита повторного использования ключа сохраняется.

Порт следующего 20-секундного слота открывается заранее. Старый сокет остаётся
на 15 секунд; принимаются соседние слоты ключей, действует анти-replay.
Согласованный HMAC-порядок портов исключает повтор соседних слотов, включая
границы блоков перестановки. Оба peer должны использовать одинаковую версию
алгоритма; порядок портов отличается от ранней версии прототипа.
ReadBatch/WriteBatch используют до 32 сообщений, буферы переиспользуются через
sync.Pool. SealInto/OpenInto не выделяют память на каждый пакет в прогретом
микробенчмарке. Это не означает отсутствие выделений в полном сетевом тракте.

Для каждого сокета запрашиваются буферы 8 МиБ. На Linux SO_RCVBUF/SO_SNDBUF
должны показать не меньше 16 МиБ с учётом двойного учёта ядра; иначе запуск
отказывает с объяснением. Стенд должен заранее задать net.core.rmem_max и
net.core.wmem_max не меньше 8388608, сохранив и затем восстановив прежние значения.
Штатная установка панели эти параметры для прототипа не меняет.

`sudo python3 tests/tunnel_namespace.py --run --binary ./mdnt-tunnel` проверяет
два настоящих TUN peer через veth в отдельных namespace: DF1352, UDP iperf120с,
смену портов, потери, CPU обоих процессов и RTT. Ключ, процессы, интерфейсы,
namespace и временные файлы удаляются в finally; без --run выводится только план.
Тест требует уже подготовленных лимитов socket buffers и установленного iperf3.
`--strict-performance` дополнительно делает превышение 15% CPU любого peer
или отклонение максимального RTT от медианы больше 20 мс ошибкой приёмки.
Без этого параметра CI проверяет функциональную ротацию и потери, а CPU/RTT
публикует как измерения, не объявляя выполнение требований производительности.
`--profile-dir` сохраняет CPU-профили в заранее созданный закрытый каталог;
для самостоятельного запуска демона доступен необязательный `--cpu-profile`.

## Дополнительный Linux offload

Флаги `--tun-offload --udp-gso` включают отдельный экспериментальный тракт.
TUN GSO/GRO обслуживает закреплённая версия пакета
[WireGuard-Go tun](https://pkg.go.dev/golang.zx2c4.com/wireguard/tun).
UDP segmentation и receive offload используют
[Linux UDP_SEGMENT/UDP_GRO](https://man7.org/linux/man-pages/man7/udp.7.html).
Без этих флагов сохраняется обычный тракт; рабочая панель их не запускает.

Для группировки шифротекста длина padding выбирается из нескольких допустимых
размеров с шагом 32 байта, сами байты остаются криптографически случайными.
Padding по-прежнему 16–128 байт, отдельная UDP-датаграмма не превышает 1452 байт.
Перестановка ограничена группами по 32 пакета, внутри окна анти-replay.
GRO-границы проверяются, усечённые сообщения отвергаются; каждый сегмент проходит
AEAD и анти-replay до передачи в TUN. Большой внутренний GSO-буфер не становится
одним IP-фрагментом: ядро сегментирует его на отдельные датаграммы.

Системная поддержка обязательна для выбранного режима: неподдерживаемая операция
приводит к ошибке. Автоматическое переключение посередине сеанса не выполняется.
Вариант проверяется на Linux 6.8; совместимость с другими ядрами требует испытания.
Пакеты TUN ограничены размером, сообщаемым адаптером (не более 128), сетевые
ReadBatch/WriteBatch — 32 сообщения. Память выделяется при создании рабочих
буферов и затем переиспользуется.

Для воспроизводимого замера доступны `--tcp --offload --pin-cpus --warmup 5`
у namespace-стенда и `GOMAXPROCS=1` у тестовых процессов. Разнесение peer и
генераторов требует четырёх CPU. Прогрев явно исключён из периода измерения.
TCP-результат не выдаётся за измерение потерь UDP.
